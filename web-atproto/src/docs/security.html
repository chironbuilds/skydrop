Trust boundaries

This layer is testnet software with internal review and no third-party audit. This page sets out what it guarantees and, just as importantly, what it can't.

What a proof establishes

  • A signing key was valid for this DID, by walking the signed PLC log from a genesis operation whose hash is the DID.
  • That key signed a repo commit, using low-S signatures, with the DID and version checked.
  • That commit holds this exact record, by hashes from the signed root down to the record's bytes.

Everything else is read from bytes those steps have authenticated. The CBOR reader doesn't enforce canonical form on purpose: non-canonical bytes only let an account mangle its own data, and every datum is covered by a signature or a hash. Any new path that reads a field without that coverage breaks this guarantee.

What a funder has to get right

  • Choose vouchers carefully. Whoever controls a voucher account controls who qualifies. If that account is compromised, so is the campaign.
  • Check an allocation list. The contract enforces the root it was given, not whether the list is fair.
  • Fund enough. A claim fails once the pool can't cover it, and first come is first served.
  • Consider the rules where you are. Offering rewards can carry legal and tax obligations, which this software knows nothing about.

Known open issue: LinkRegistry capacity

The LinkRegistry keeps every link and chain floor in one component, capped at 1 MiB, and that needs fixing before mainnet. Anyone can add entries with self-made identities for only the transaction fee. Every Campaign claim reads the registry for the chain floor, so a bloated registry raises everyone's claim cost, and a full one stops new key rotations and links being recorded. The Escrow's fix doesn't carry over directly: a contract can't ask whether a record exists, and a floor has to be readable for accounts that have never been seen.

Bugs found so far

Internal review of the policy stack found and fixed these before any real funds were at risk. Listed because more of the same kind may remain.

  • Unchecked metadata arithmetic let a dust deposit with a huge window block every claim for an account.
  • A key rotated away could still claim, because the floor wasn't shared across policies.
  • An unauthenticated setter could have been front-run to point linked payouts at a fake registry.
  • A single per-account deposit cap let a stranger fill a victim's slots. Caps are now per policy.
  • A junk slot at the front of a bounty pool could block every claim. Campaign ids now name their funder.
  • Every deposit lived in one 1 MiB component, so anyone could fill the shared Escrow with dust and block new deposits for everyone. Each account now has its own ledger, and nothing shared grows with deposits.

Reporting a problem

Open an issue or a private security advisory on the repository. The live proof page has a tamper test, and if any of those checks passes, that's a bug worth reporting.
