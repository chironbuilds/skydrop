The Campaign contract

A campaign is one funded pool with a set of rules, deployed as its own component. Anyone can create one. No governance approves it, and after creation nobody has authority over it except the funder, who can only extend the close date or collect what's left once it has closed.

Why each campaign is its own component

A substate is capped at 1 MiB, and every call that touches a component pays to load it. A set of claimant DIDs held in component state would reach that cap at around 30,000 claimants, and claims would get more expensive all the way there. So Campaign stores nothing per claimant in its own state:

  • Double claims are stopped by a receipt NFT. Its id is the hash of the DID, so minting it a second time fails the transaction. In the test suite, five claims changed the component's state by 4 bytes.
  • Receipts are soulbound. They can't be withdrawn from the account they arrive in, so they double as a permanent record of taking part.
  • Campaigns are isolated. Each has its own vault and can pay in any fungible resource, and a problem with one can't reach another's funds.

Claims within one campaign still run one at a time, because each one updates the same vault. Expect contention during a rush, not failure.

Rules

A claimant must prove every rule, up to eight. Rule kinds are numbered in the contract.

Rules can repeat and can each point somewhere different, so "like post X, like post Y, repost post Z" is three rules. The contract requires all of them but can't check their order: accounts sign their own timestamps, so "do this first" isn't enforceable.

Either/or: rules sharing a non-zero groups value need only one proof; leave the others' commits empty. Required wording: a reply or quote rule can set texts, which that same post must contain. A contract can check that a string is present, not whether the comment is any good.

Vouch rules (6 to 8) are the ones that limit fake accounts, because someone else's signature decides who qualifies. Each can also set a snapshot: the proof must come from one of the voucher's commits at or after that time.

Creating a campaign

Campaign::create(name, info, funder, link_registry, kinds, targets, snapshots, texts, groups, reward, allocation_root, rounds, round_epochs, referral_bonus, max_referrals, open_epoch, close_epoch, funds)

funder must sign. kinds, targets, snapshots, texts and groups are parallel lists. It emits a campaign.created event naming the funder, so a funder's campaigns can be found later. An empty allocation_root pays everyone reward. The close epoch can be at most 20,000 epochs away.

Claiming

claim(did, claimant, account, ops, commits, nodes, records, rkeys, vouch_ops, c_commit, c_nodes, c_record, c_rkey, amount, path, referrer)

The first claim. claimant signs, and a post in the DID's repo must contain the code from expected_post_text, which commits to this campaign, the DID, the wallet key and the round. There is one proof per rule, in rule order, plus the voucher's identity log for each vouch rule. amount and path prove an allocation.

claim_linked(did, ops, commits, nodes, records, rkeys, vouch_ops, amount, path, referrer)

For an account that has already linked a wallet in the LinkRegistry. It needs no code post and no signature, because the registry already binds the DID to its wallet. Anyone may submit it, so a relayer can pay the fee for the user.

claim_round(did, claimant, ops, commits, nodes, records, rkeys, vouch_ops, c_commit, c_nodes, c_record, c_rkey, amount, path)

A later round. It needs round_epochs since the last payment, a new code post for this round, and a re-proof of every rule from a commit newer than the last one proven. It pays the account on the receipt.

Every account a claim proves, the claimant's and each voucher's, needs a record in the LinkRegistry. A claim fails without one, so a client adds open_account(did) to the same transaction for any DID that doesn't have a record yet. That's the only way to read a floor of 0, so it can't be used to skip a floor that exists.

The funder's limits

top_up(funds)

Anyone can add to the pool.

extend(close_epoch)

Funder only, and later only. Nobody loses a window they were promised.

close() → Bucket

Funder only, and only from the close epoch onward. Rounds not claimed by then are forfeited.

When the pool can't cover a reward, the claim fails instead of paying less. Funding a pool for fewer people than qualify means late claimers get nothing, so size it deliberately.

Reading a campaign

stats() → (claimants, payments, paid, balance, open_epoch, close_epoch)

The campaign's public numbers. It also emits a campaign.claim event per payment.

expected_post_text(did, claimant, round)

The exact code a claimant must post.

receipt_resource()

The resource address of this campaign's receipts.

Allocation lists

A list of any size goes on-chain as one 32-byte root. Leaves and inner nodes use different prefixes, so an inner node can't be passed off as a leaf:

leaf  = sha256(0x00 || did || 0x00 || amount as 8 bytes, big-endian)
inner = sha256(0x01 || smaller child || larger child)

The campaign builder computes the root and each account's proof, and a funder should publish the full list so anyone can recompute it. The funder is trusted to get the list right, and nothing on-chain can tell if it's unfair.

Each extra identity operation costs about one more signature check, and P-256 keys cost roughly five times what k256 keys do.
