Custody, verification, and features — kept apart

Ootle templates are immutable and a component is bound to its template for life. So the component that holds funds must never need new code: everything that changes lives in policies the vault delegates to. A new feature is a new policy plus one badge — the escrow is never redeployed, and no deposit is ever orphaned by an upgrade.

Release is authenticated the Radix/Ootle way: the engine can't tell a method who called it, so each approved policy holds a unique NFT badge. release takes a Proof of it, reads the badge's id, and confirms it matches the deposit's pinned policy — a policy can only ever move its own deposits.

The Escrow interface

Small and frozen on purpose. These are the only methods that move funds; a policy never holds the escrowed vault, only its badge.

open_account(account_id)

Creates the account's own ledger. Anyone may call it, and the caller pays for the storage. It fails if the ledger exists, because a contract can't ask whether a record exists, so a client checks first and sends this with the first deposit.

deposit(account_id, sender, refund_epoch, policy, metadata, funds)

Escrow funds for an account, pinned to the governing policy. metadata is opaque bytes the policy defines — the escrow never reads it.

policy_deposit(badge: Proof, account_id, sender, refund_epoch, policy, metadata, funds)

Escrow on a policy's behalf, authorized by its badge instead of a sender signature — for funds a policy controls, like a relayed tip from a budget or the unspent remainder of a credit line.

release(badge: Proof, account_id, index) → Bucket

Pay out one deposit. Authorized by a proof of the policy's badge; the badge id must equal the deposit's pinned policy, so no policy can touch another's funds.

release_to(badge: Proof, account_id, index, to)

Like release, but deposits straight into an account the policy has validated — a DID's linked wallet, or the new owner a recovery chose.

return_to_sender(badge: Proof, account_id, index)

Hand a deposit back to its sender early (a declined gift, an invalid one). It stays in the ledger, out of every policy's reach, and the sender collects it with refund right away.

refund(account_id, index) → Bucket

Return a deposit to its sender after its refund epoch. Needs no badge — the safety valve that works even if a policy is buggy or retired.

approve_policy(policy) → Bucket

Governance only (admin signature). Mints the policy's unique badge NFT; route the bucket into the policy's receive_badge.

deposits_for(account_id) → Vec<Deposit>

Every deposit for an account across all policies — the single place clients read, so funds are never stranded in a superseded component.

Authorizing a policy

A new feature joins the system in four steps. After this the policy can release its own deposits forever, with no further escrow changes.

1

Deploy the Escrow once

Escrow::new(resource, min_deposit, admin, ledger_vault_size). This is permanent; every future feature reuses it.

2

Deploy your policy

MyPolicy::new(escrow, escrow.policy_badge_resource(), link_registry) — the policy makes an empty vault for the badge it's about to receive, and pins the shared LinkRegistry whose chain_pin it checks.

3

Governance approves it

The admin calls escrow.approve_policy(my_policy) and routes the returned badge into my_policy.receive_badge(badge) in one transaction.

4

It's live

Senders can now escrow deposits pinned to the policy, and the policy releases them by presenting its badge. No escrow redeploy, and existing deposits never move.

The badge is a bearer token. Authority rests on holding the badge, so it stays in the policy's vault and is never withdrawn — the standard capability pattern. Governance vets a policy's code before approving it, because an approved policy can release the deposits pinned to it (never another policy's, never past refund).

Deposits & metadata

A deposit is (sender, amount, refund_epoch, policy, metadata, created_epoch). The escrow stores it and checks the resource, minimum and refund epoch; everything feature-specific lives in metadata, which only the policy interprets. ClaimPolicy, for example, encodes the challenge window as a big-endian u64:

Bounded by design. Metadata is capped at 256 bytes, a refund epoch can be at most 20 000 epochs out, and each account holds at most 64 deposits per policy (512 in all). Lanes are per policy so that someone spamming dust under one feature can never block deposits for the same account under another. Each account's deposits sit in its own ledger NFT, whose id is the SHA-256 of the account id, so the worst a stranger can do is fill one account's lane, never the Escrow itself.
// sender side: a 3-epoch challenge window
let metadata = Bytes::from_vec(3u64.to_be_bytes().to_vec());

// policy side: read it back, empty/short means 0 = pay immediately
fn window_of(m: &Bytes) -> u64 {
    let b = m.as_slice();
    if b.len() >= 8 { u64::from_be_bytes(b[..8].try_into().unwrap()) } else { 0 }
